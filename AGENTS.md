# Project Architecture Rules

- Order list reads never mutate reopen state; callback completion is scoped to the latest reopen or active scheduler cycle so historical completions cannot erase a new escalation.

- Run production and preview builds with a 6 GB Node heap because the combined TanStack Start and Nitro server bundle exceeds Node's default heap limit.
- Generate exact stored-email dispute PDFs in the authorised CRM browser, then upload the finished PDF through an authenticated server function because the deployed server has no HTML layout engine.- Employee Performance historical KPIs come only from the `get_employee_perf_stream` database function (order-level events, validated human actors, IST ranges) aggregated by `src/lib/crm/perf-engine`, because assignment custody and work credit must never be reconstructed from `applications.assigned_to`.
- Order ownership changes go through the `assign_application` database function (row-locked, compare-and-set, server-only) so the ownership update and its `application_events` history row commit atomically with an explicit actor type.
- Customer Document Merge reuses the shared browser pdf-lib merge in src/lib/disputes/dispute-browser-pdf.ts (appendFileToPdf) and saves through the existing order document upload, so there is one PDF engine and one document store.
- Keep the first NIC activity in the existing nic_2_digit/nic_4_digit/nic_5_digit form answers and store additional activities in nic_activities in the same submission, so older forms and order views remain compatible.
- Add NIC activity fields through the form builder as the canonical 2/4/5-digit trio with shared visibility, so the customer form renders one search and activity list while retaining compatible answers.
- Flatten saved form-builder sections with display-only section headings for customer forms and previews, so section boundaries remain visible without changing submitted answers.
- CallerDesk is the only telephony provider: outbound calls use click_to_call_v4 with a validated member id (profile mapping, else mobile match) and never fall back, because silent fallbacks hid failed calls. Historical smartflo rows and the legacy profiles.smartflo_agent_id column (now the optional CallerDesk Member ID) are kept for history.
- CallerDesk browser calling (SIP.js over WSS) is gated by CALLERDESK_WEBRTC_ENABLED plus the signed-in employee's own active employee_telephony_accounts row, and that SIP secret is released only to that employee in memory, because SIP digest auth must run in the browser.
- CallerDesk IVR administration stores validated, revision-checked drafts in callerdesk_ivr_settings; it never claims provider synchronization or activates routes until a documented configuration API is implemented, because the verified setup method is currently the CallerDesk portal.
- SIP passwords live only as AES-256-GCM ciphertext (TELEPHONY_CREDENTIAL_KEY, employee id as AAD) in a service-role-only table; legacy env credentials stay as a rollback for the original agent until a vault row exists, because rows must not be readable by clients or reusable across employees.
- Incoming-caller identification uses the staff-only lookupCaller (phone.server) and never auto-picks among multiple orders; inbound browser calls are recorded once under call_id webrtc:in:<client key> and the webhook adopts them only on a single unambiguous match, because SIP Call-ID and CallerDesk CallSid are not shared.
- CRM records start browser calls only through the single admin-mounted browser phone via src/lib/telephony/browser-phone-bus, and post-call wrap-ups create follow-ups in the existing follow_ups table, because duplicate phone engines or a separate notes store would split call state.
- Customer pages and their server functions authorize only through scoped customer access tokens (src/lib/security/customer-access*; SHA-256 hashes in customer_access_tokens, raw token in the URL fragment and browser storage), never by lead code or order id, because sequential codes are guessable. Outgoing emails get tokens added automatically in enqueueEmailInternal; payment gateway returns get a fresh token on the starting site only when they carry the per-payment return secret, because gateway callbacks can be forged.
- Customer page URLs carry leads.public_ref (random 32-hex id) instead of the lead code; CustomerRefGate maps it back and swaps code URLs to the ref once the browser proves a valid link, and email/gateway links are built with the ref, because sequential codes in the address bar are guessable.
- Cashfree payments pick a merchant account only from an explicit cashfree_website_accounts mapping on the lead's stored website_id, record it immutably in payments.payment_account_id, and webhooks/status checks use that recorded account (NULL = historical legacy); no global fallback, because each site can have its own merchant account and credentials stay in server secrets.
- Website-wise payment options live in website_payment_gateways (server-only) and can only narrow the global payment_gateways switch; no row means follow the global switch, and every order builder re-checks the lead's stored website, because hidden options must not be reachable by a crafted request.
- Shared websiteGatewayRules additionally suppresses Cashfree unless its explicit website mapping resolves usable credentials, so customer summaries and both default-payment initiators cannot advertise an unconfigured account; other providers keep their existing switches.
- Cashfree merchant account keys entered in the admin screen live only as AES-256-GCM ciphertext (PAYMENT_CREDENTIAL_KEY, account id as AAD) in the service-role-only cashfree_account_credentials table; the legacy account keeps using the global secrets, and only super admins can save keys or link websites, because payment secrets must never reach browsers or be reusable across accounts.
